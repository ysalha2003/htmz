# 01 — الجدوى والقيمة: هل يستحق HTMZ Kit البناء؟

> ملخص القرار: **CONDITIONAL GO** (استمرار مشروط). الفكرة جديرة بالاستثمار **بشرط** تغيير آلية النقل من الإطار المخفي إلى طبقة Fetch اختيارية فوق تطبيق صفحات كاملة، وبشرط اجتياز بوابة المرحلة 1. التفاصيل في الوثيقتين 04 و10.

## 1. هل هذا يستحق البناء؟

### 1.1 ما الحاجة الحقيقية؟

فرق صغيرة ومتوسطة تبني تطبيقات أعمال (لوحات إدارة، بوابات عملاء، أدوات داخلية، أنظمة CRUD) وتعاني من:

- **كلفة الأدوات:** تثبيت Node وحزم بمئات الميغابايت ومُجمِّع ومعالِج CSS لمجرد إظهار نموذج.
- **كلفة التعلّم:** إطار واجهة + موجّه + مدير حالة + مكتبة نماذج + نظام تصميم، لكل مشروع.
- **كلفة الصيانة:** ترقيات متتابعة للتبعيات، وتوقف المشاريع القديمة عن البناء بعد سنة.
- **ضعف العربية وRTL:** معظم أنظمة التصميم الجاهزة تعامل RTL كإضافة لاحقة، وتختار خطوطًا ومسافات غير مناسبة للعربية.
- **الجوال كفكرة لاحقة:** التخطيطات تُصمم لسطح المكتب ثم «تُكسر» للجوال.

البحث في الوثيقة 03 يبيّن أن منصة الويب نفسها أصبحت تغطي معظم ما كانت الأطر تغطيه: حوارات، قوائم منبثقة، أكورديون، تحقق، طبقات CSS، استعلامات حاوية، تداخل، ألوان حديثة. **الفجوة المتبقية صغيرة ومحددة:** التحديث الجزئي للصفحة، ونظام تصميم جاهز، وانضباط هندسي.

### 1.2 ما الميزة الهندسية الفعلية مقارنة بالبدائل؟

| البديل | ما يقدمه | ما ينقصه بالنسبة لهدفنا |
|---|---|---|
| تطبيق صفحات كاملة عادي (Django/Laravel/Rails + CSS يدوي) | أبسط ما يمكن | لا نظام تصميم، لا تحديث جزئي، كل فريق يعيد اختراع RTL والجوال |
| htmx + أي نظام تصميم | تحديث جزئي ناضج | تبعية طرف ثالث، DSL من السمات، نظام التصميم ليس عربيًا ولا Mobile-First |
| React/Vue + مكتبة مكوّنات | كل شيء | خطوة بناء إلزامية، مئات التبعيات، JavaScript لكل شيء، كلفة صيانة عالية |
| Bootstrap/Tailwind + JS يدوي | تصميم جاهز | Bootstrap يحمل JS خاصًا به؛ Tailwind يحتاج بناء؛ RTL إضافة لاحقة |
| **HTMZ Kit المقترح** | صفحات كاملة + طبقة تحسين ≤ 5 كيلوبايت + نظام تصميم عربي أولًا بلا بناء + عقد خادم بسيط + مولّد + اختبارات | لا يغطي التطبيقات عالية التفاعل (بالتصميم) |

الميزة الحقيقية **ليست** الحجم الصغير بحد ذاته، بل **الحزمة المتكاملة بلا بناء**: مطور يكتب HTML وCSS ويُعيد HTML من أي خادم، ويحصل على تطبيق محترف، عربي، متجاوب، متاح، مع اختبارات متصفح حقيقية، دون أن يثبّت شيئًا في المتصفح.

### 1.3 هل البناء مبرر اقتصاديًا؟

- حجم العمل المقدّر: **16–24 أسبوع عمل هندسي** لمهندس أول واحد (الوثيقة 08)، أي 4–6 أشهر تقويمية لشخص واحد، أو 3–4 أشهر لشخصين.
- ما يُشترى بهذا الاستثمار: أساس يُستخدم في كل مشروع لاحق، وكلفة صيانته تنخفض مع الوقت لأن المنصة تتحمل العبء لا المكتبة.
- نقطة التعادل: إذا كان الفريق يبني أكثر من تطبيقين أو ثلاثة من الفئة المستهدفة خلال سنتين، فالاستثمار يُسترد. إذا كان تطبيقًا واحدًا، فالأفضل بناؤه مباشرة بتطبيق صفحات كاملة + htmx.

## 2. من سيستخدمه؟

### 2.1 المستخدمون المستهدفون

- مطورو الخلفية (Python، PHP، Go، Java، C#، Node) الذين يريدون واجهة محترفة دون أن يصبحوا مطوري واجهات.
- فرق صغيرة (1–5 أشخاص) تملك المشروع لسنوات وتخشى تآكل التبعيات.
- المؤسسات العربية التي تحتاج RTL أصيلًا وعربية صحيحة لا مترجمة.
- فرق تعمل في بيئات مقيدة (لا يُسمح بـ npm في الإنتاج، أو CSP صارم إلزامي).

### 2.2 فئات التطبيقات المناسبة

| الفئة | الملاءمة | ملاحظة |
|---|---|---|
| تطبيقات الأعمال الصغيرة (عملاء، فواتير، طلبات) | **ممتازة** | نماذج + قوائم + تفاصيل + بحث |
| الأدوات الداخلية | **ممتازة** | المستخدمون معروفون والمتصفحات محكومة |
| لوحات الإدارة | **جيدة** | الجداول والفلاتر تحتاج عناية في الجوال |
| تطبيقات CRUD | **ممتازة** | هذا هو النمط الأصلي للويب |
| مساحات عمل المشاريع | **جيدة** | ما لم تحتج تعاونًا لحظيًا |
| بوابات عملاء خفيفة | **جيدة** | مع انتباه للأداء على الأجهزة المتواضعة |
| أنظمة أعمال مولَّدة من الخادم | **ممتازة** | المعمارية تطابق ما تفعله الأنظمة أصلًا |

## 3. أين سيتعثر؟

| فئة التطبيق | التقييم | هل دعمها يدمّر البساطة؟ |
|---|---|---|
| محررات غنية (نص، مخططات، جداول بيانات) | غير مناسب كأساس | نعم إن حاولنا؛ الحل: عنصر مخصص أو مكتبة مستقلة داخل منطقة واحدة، خارج نطاق العدة |
| تطبيقات بلا اتصال (Offline-first) | غير مناسب | نعم؛ تحتاج Service Worker ومزامنة حالة، وهذا منتج آخر |
| عرض بيانات لحظي (رسوم حية، تداول) | غير مناسب للتدفق المستمر | جزئيًا؛ إعادة جلب دورية لمنطقة ممكنة، أما التدفق الحقيقي فيحتاج SSE/WebSocket خارج العدة |
| حالة عميل معقدة متزامنة (سلّة متعددة الخطوات، سحب وإفلات) | مناسب جزئيًا | يمكن احتواؤه في جزيرة JS مستقلة، لكن ليس في النواة |
| تطبيقات بآلاف الصفوف تُفلتر لحظيًا | مناسب مع إعادة جلب من الخادم | لا، إن قبل الفريق أن الفلترة في الخادم |
| ألعاب، رسوم، صوت وفيديو تفاعلي | غير مناسب | نعم |

**الموقف:** هذه الفئات ليست مستحيلة، لكن دعمها في النواة سيجعل العدة إطارًا آخر. القاعدة: **العدة تملك الصفحة والتخطيط والنماذج، وأي «جزيرة» تفاعلية معقدة تُعزل في عنصر مخصص أو مكتبة مستقلة** تُستبدل كوحدة واحدة.

## 4. المقارنة الصريحة

| المعيار | HTMZ Kit المقترح | htmx + Bootstrap | React + MUI/shadcn | صفحات كاملة بلا عدة |
|---|---|---|---|---|
| منحنى التعلّم | HTML + CSS + سمة واحدة | HTML + ~30 سمة + Bootstrap | JSX + Hooks + أدوات | HTML + CSS |
| سرعة التسليم | عالية بعد المولّد | عالية | متوسطة (إعداد) | متوسطة (كل شيء يدوي) |
| حجم التشغيل في المتصفح | ≤ 5 كيلوبايت JS + ~10–15 كيلوبايت CSS (هدف) | ~14 كيلوبايت JS + ~25 كيلوبايت CSS | 100+ كيلوبايت | 0 + CSS يدوي |
| عبء التبعيات | صفر في المتصفح؛ Playwright للتطوير فقط | مكتبتان | مئات الحزم | صفر |
| الصيانة طويلة الأمد | منخفضة (منصة) | منخفضة إلى متوسطة | عالية | منخفضة |
| السلوك الأصلي | كامل (روابط، نماذج، تاريخ) | شبه كامل | مُعاد تنفيذه | كامل |
| تعقيد الأمان | ترميز خادم + CSP | ترميز خادم + CSP + تعطيل تنفيذ السكربتات | XSS أقل في القوالب، لكن سطح أكبر | ترميز خادم + CSP |
| مرونة الخادم | أي خادم يُخرج HTML | أي خادم | يحتاج API JSON غالبًا | أي خادم |
| الاستدامة | تعتمد على المعايير | تعتمد على مشروع مفتوح نشط | تعتمد على نظام بيئي سريع التغير | تعتمد على المعايير |

أرقام الأحجام للبدائل تقريبية من مواقعها الرسمية ولا تُستخدم كادعاء أداء؛ أرقام HTMZ Kit **أهداف** لا قياسات.

## 5. البناء أم التبني؟

- **لا نبني** مكتبة تحديث جزئي عامة تنافس htmx في اتساعه. نبني **ملفًا صغيرًا مقيّدًا** بثمانية سلوكيات مع بوابة تراجع إلى htmx (الوثيقة 04، القسم 6).
- **لا نبني** موجّهًا ولا مدير حالة ولا مكوّنات JS.
- **نبني** ما لا يوجد له بديل جاهز يلبي الشروط: نظام تصميم عربي أولًا، Mobile-First، بطبقات CSS أصلية، مع فاحص بلا تبعيات، ومولّد، وعقد خادم موثق، وتطبيق مرجعي، واختبارات متصفح.
- **نتبنى** أدوات التطوير الاختيارية الناضجة: Playwright للاختبار، axe-core لفحص الوصول، وربما Stylelint. كلها خارج المتصفح وخارج الإنتاج.

## 6. الشروط التي يتوقف عليها «GO»

1. اعتماد تغيير آلية النقل (الوثيقة 04). بدون هذا الشرط القرار **NO-GO** لأن الإطار المخفي لا يحقق «موثوق ومتاح وآمن بالتصميم».
2. اجتياز بوابة المرحلة 1: الطبقة ≤ 5 كيلوبايت مضغوطًا، تجتاز مصفوفة المتصفحات الثلاثة بما فيها سيناريوهات تعطيل JavaScript والرجوع وإعادة التوجيه والمهلة.
3. وجود التزام بتطبيق مرجعي واحد حقيقي (المرحلة 4) يُقاس عليه النجاح، لا عروض توضيحية.
4. تخصيص الجهد المقدّر (16–24 أسبوعًا) فعليًا، وإلا يُفضَّل تبنّي htmx مع نظام تصميم خاص فقط.
